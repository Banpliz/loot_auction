# Аукцион лута — статус на 2026-08-27

Telegram Mini App: админ грузит скриншоты внутриигрового аукциона, приложение
режет их на лоты по иконке предмета, определяет цвет редкости, пользователи
делают ставки, админ разыгрывает победителей с лимитами по цвету. OCR и цена
полностью выпилены (не читаем текст со скриншота вообще).

## Стек

Fastify + better-sqlite3 + sharp + ваниль TS/Vite фронтенд, Telegraf-бот.
Auth — Telegram initData (HMAC).

## Важная особенность машины

На локальной Windows-машине **нет инструментов сборки** (Visual Studio Build
Tools). `npm install`/`npm uninstall` без явной нужды может попытаться
пересобрать нативные модули (`better-sqlite3`) и **снести node_modules
целиком** — уже случалось. Ставить новые зависимости — только по одной,
сразу проверяя, что тесты/сборка не сломались. **Не запускать install/
uninstall без явного запроса пользователя** — было отдельно оговорено. На
VPS это не так критично, но `npm install` там гонять тоже только когда в
`package.json` реально что-то новое.

Также у better-sqlite3 в этой сборке **внешние ключи включены по умолчанию**
(`PRAGMA foreign_keys = 1`), в отличие от типичного поведения SQLite. Это
была реальная причина бага ниже — при написании новых DELETE-транзакций
держать это в уме и чистить все зависимые таблицы, а не полагаться на то,
что FK выключены.

## Схема БД (текущая)

`users`, `events`, `screenshots` (event_id, original_path, rows, template,
uploaded_by), `items` (event_id, screenshot_id, color, category, quantity,
image_path, status), `claims`, `item_winners` (item_id, telegram_id — лот с
quantity > 1 разыгрывает несколько разных победителей из тех, кто на него
ставил), `lot_library` (icon_signature, name, category — см. отдельный
раздел ниже). `price` в `items` — мёртвая колонка с дефолтом, никем не
читается; `name` теперь живая (ручная пометка + автоподстановка из
lot_library). Таблиц `settings`/`price_tiers`/`catalog_items` больше нет.

Миграция в `src/server/db.ts` — не пошаговая, а drop+recreate: при
обнаружении старых колонок (`catalog_item_id`, потом `winner_telegram_id`)
таблицы `items`/`screenshots`/`claims`/`item_winners` дропаются и создаются
заново с текущей схемой. Осознанно, т.к. продакшен-данных пока нет.

## Правило лимитов побед (зашито в коде, не настраивается)

В `src/server/routes/events.ts` (`winLimitGroup`) правило зависит от
`screenshots.template` того лота, а не от ивента в целом:
- **invasion** — по цвету, как раньше: фиолетовый+красный вместе максимум
  **1** победа на человека за ивент, синий — **2**.
- **feast** — по `items.category` (не по цвету!): обычные предметы
  (`item`) максимум **1**, камни закалки (`stone`) — **3**. Это правило
  альянса пользователя, независимый счётчик от предметов.

Ставок можно делать сколько угодно, лимит только на выигрыш.

## Категория лота: Предмет/Камень (`items.category`)

Только для feast, ставится **вручную** в админке (выпадающий список рядом с
цветом) — автоопределение по картинке сознательно не делали: слишком легко
ошибиться и дать/забрать лишний выигрыш. Дефолт — `item`. Пользователь уже
один раз спрашивал про автоопределение (2026-08-28) и явно выбрал оставить
вручную — не предлагать эвристику повторно без нового запроса.

## Дедуп лотов по иконке (`src/server/dedup.ts`)

Иконки сравниваются через downscaled-thumbnail фингерпринт (16×16, mean
per-byte diff, порог 8 — откалибровано на реальном скриншоте 2026-08-27).
Дедуп работает в два прохода: сначала группирует повторы внутри одной
загрузки (`groupBySignature`), затем отдельно сверяет каждую итоговую группу
с тем, что уже лежит в пуле этого ивента (`isSameIcon`) — так ловятся
повторы **между разными** загрузками скриншотов, а не только внутри одного
запроса. При совпадении лоту просто увеличивается `quantity`, новый лот не
создаётся.

## Библиотека лотов (`src/server/lot-library.ts`, таблица `lot_library`)

Чтобы админ не перевыставлял вручную название/категорию одного и того же
предмета на каждом новом ивенте: ключ — тот же icon-signature фингерпринт,
что и в dedup.ts (`isSameIcon`, порог 8), без привязки к событию — иконка
предмета выглядит одинаково везде, где он выпадает.

- Запись: в `PUT /items/:id` (`items.ts`) — если админ прислал `name` и/или
  `category`, после апдейта берётся текущее состояние строки и
  `rememberLot()` сохраняет его в библиотеку (апсерт по совпадающей
  иконке). Ошибка чтения файла иконки (напр. в тестах путь фиктивный) —
  проглатывается с warning, не роняет запрос.
- Чтение: в `POST /events/:id/screenshots` (`screenshots.ts`) — для каждого
  **нового** лота (не для тех, что смёржились в уже существующий по dedup)
  сигнатура иконки ищется в библиотеке через `findInLibrary()`; при
  совпадении `name`/`category` подставляются сразу при создании лота.
- Универсальная иконка сундука (`isGenericChestIcon` из dedup.ts)
  исключена из поиска по библиотеке по той же причине, что и из
  кросс-загрузочного dedup: она одинакова у разных по содержимому сундуков,
  так что "запомненное" имя/категория того сундука, который затегали
  первым, разъедется с реальным содержимым следующих.
- Библиотека не различает feast/invasion явно — но иконка одного и того же
  предмета в разных шаблонах обычно и выглядит по-разному (разная рамка/
  бейдж), так что записи и так фактически не путаются между шаблонами.

## Фиксы ставок 2026-08-28 (`web/views/pool.ts`, `src/server/routes/items.ts`)

- **Скролл при ставке**: клик на «Ставка» вызывал `renderPool()` целиком —
  тот сбрасывал `root.innerHTML` на спиннер и пересобирал страницу с нуля,
  из-за чего скролл прыгал наверх. Теперь после клика перерисовывается
  только список лотов (`renderFiltered`), сам компонент не пересоздаётся.
- **Ставка после дедлайна**: `POST /items/:id/claim` вообще не проверял
  `events.deadline_at` — ставку можно было отправить и через API напрямую,
  и просто оставив вкладку открытой после конца приёма заявок. Теперь
  бэкенд отклоняет с 409, а кнопка «Ставка» в UI прячется при достижении
  дедлайна (проверка при рендере + один раз на переходе открыто→закрыто в
  таймере обратного отсчёта, не на каждый тик).

## Исправлено и задеплоено 2026-08-27: 500-ошибка при удалении ивента

`DELETE /events/:id` чистил `claims`, `items`, `screenshots`, но не
`item_winners`. Раз в этой сборке better-sqlite3 внешние ключи включены по
умолчанию, удаление `items` при висящих ссылках из `item_winners` падало с
`FOREIGN KEY constraint failed` → голый 500 "Internal Server Error" на
клиенте — именно это ловил пользователь при попытке удалить уже разыгранный
ивент. Воспроизведено тестом, поправлено добавлением `DELETE FROM
item_winners WHERE item_id IN (...)` в ту же транзакцию.

Закоммичено на `main` (`5dd334f`), запушено в `origin/main`, задеплоено на
VPS (`git pull` + `npm run build:web` + `systemctl restart loot-auction`) —
сервис поднялся и слушает порт 3000. Стоит ещё раз проверить сценарием
"удалить уже разыгранный ивент" вживую в боте, чтобы закрыть вопрос
окончательно.

## Открытая проблема: нестабильная загрузка скриншотов

Симптом: при загрузке реальных скриншотов с телефона через ngrok — ошибка
503 / "Premature close". Диагностировано: файл физически не долетает до
сервера — дело не в размере файла и не в скорости обработки, а в
нестабильности/медленности канала телефон↔ngrok. На VPS с нормальным
хостингом (без ngrok) эта проблема ожидаемо не должна проявляться так же
остро — не переисследовано после переезда на VPS.

Уже сделано (`web/views/eventDetail.ts`, `src/server/routes/screenshots.ts`):
ответ отдаётся сразу после нарезки (цвет — в фоне), загрузка по одному файлу
за запрос, сжатие на клиенте (JPEG, ширина до 720px, качество 0.7),
автоповтор до 3 попыток.

## Как продолжать

1. Прод теперь обновляется штатным git-флоу — коммит на `main` → `git push`
   → на VPS `git pull` + `npm run build:web` + `systemctl restart
   loot-auction` (детали в [[loot_auction-vps-deploy]] памяти сессии).
   Копирование файлов руками (`cp`) между воркспейсом/локальной
   папкой/прод — больше не нужно и не должно применяться.
2. Локальный `npm start` — только когда точно известно, что VPS сейчас не
   поднят (иначе 409 по Telegram-токену). Для параллельной локальной
   разработки без конфликта с продом понадобится отдельный `BOT_TOKEN`
   тестового бота — сейчас его нет, используется один и тот же токен везде.
3. После правок backend — обязательно `npx vitest run` + `npx tsc --noEmit`
   перед коммитом.
4. `npm install`/`npm uninstall` — только по явному запросу пользователя,
   особенно на локальной машине (см. "Важная особенность машины").
